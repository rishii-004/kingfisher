# kingfisher — Database Guide

> How to start, access, inspect, and reset the Postgres database used
> by the backend. See `API.md` for the API contract and `TODOS.md` for
> backend completion history.

---

## Connection details

| | |
|---|---|
| Engine | PostgreSQL 16 (Docker: `postgres:16-alpine`) |
| Host / Port | `localhost:5433` (mapped from the container's `5432`) |
| Database | `kingfisher` |
| User / Password | `postgres` / `postgres` |
| Connection string | `postgresql://postgres:postgres@localhost:5433/kingfisher` |

These live in `backend/.env` (created from `backend/.env.example` on
first run) and are read by `app/config.py` via `DATABASE_URL`. Change
them there if you need a different setup — nothing else needs editing.

The port is `5433`, not Postgres's default `5432`, specifically so it
won't collide with a Postgres instance you might already have running
locally.

---

## Starting it

The database runs in Docker, defined in `backend/docker-compose.yml`
(a single `db` service — there's no backend/frontend container yet).

```bash
# Easiest: starts Postgres + backend + frontend together
cd kingfisher-parent/kingfisher && ./start.sh   # or: make dev

# Or just the database, from backend/
cd kingfisher-parent/kingfisher-backend/backend
docker compose up -d db
```

Data persists in the `pgdata` Docker volume across restarts. It's
only wiped if you explicitly remove the volume (see "Resetting"
below).

## Accessing it

**From the repo (no client install needed):**

```bash
cd kingfisher-parent/kingfisher
make db-shell
# equivalent to:
docker exec -it $(docker compose -f ../kingfisher-backend/backend/docker-compose.yml ps -q db) \
  psql -U postgres -d kingfisher
```

**With a GUI client** (TablePlus, DBeaver, Postico, pgAdmin, etc.):
point it at `localhost:5433`, database `kingfisher`, user/password
`postgres`/`postgres`.

**From Python**, if you want to poke at data directly instead of
through the API — every backend script/test in this repo does this:

```python
from app.database import SessionLocal
from app.models.user import User

db = SessionLocal()
user = db.query(User).filter(User.email == "you@example.com").first()
db.close()
```

Run this from `backend/` with `venv/bin/python`, or via
`venv/bin/python -m pytest`/`-m scripts.seed`-style module invocation
so the `app` package resolves.

## Schema

Seven tables, defined in `backend/app/models/`. No ORM-level
`relationship()` cascades are set up (only `owner = relationship(...)`
on `ProblemList` for convenience reads) — deletes that need to respect
foreign keys are handled explicitly in the routers/services, not by
the database or ORM automatically.

| Table | Purpose | Key columns |
|---|---|---|
| `users` | Accounts | `id`, `email`, `username`, `hashed_password`, `is_admin`, `created_at`, `updated_at` |
| `problems` | Global problem catalog | `id`, `title`, `slug` (unique), `platform`, `platform_url`, `difficulty`, `topic_tags` (array), `company_tags` (array) |
| `lists` | Problem lists — both global (admin-curated) and custom (user-owned/forked) | `id`, `name`, `description`, `is_global`, `is_custom`, `owner_id` → `users.id` (null for global), `forked_from_id` → `lists.id` (null unless this is a fork) |
| `list_problems` | Join table: which problems are in which list, in what order | `list_id` + `problem_id` (composite PK) → `lists`/`problems`, `order` |
| `user_problems` | Per-user status on a problem | `user_id` + `problem_id` (composite PK), `status` (`todo`/`solving`/`solved`/`skipped`), `solved_at` |
| `solve_logs` | Post-solve notes for a solved problem | `id`, `user_id`, `problem_id`, `mistake_tags` (array), `notes`, `time_spent`, `solved_at` |
| `reviews` | Scheduled spaced-repetition reviews | `id`, `user_id`, `problem_id`, `solve_log_id` → `solve_logs.id` (nullable), `interval_days`, `due_at`, `review_stage`, `last_reviewed_at` |

**FK order matters when deleting by hand:** `reviews.solve_log_id`
points at `solve_logs`, so delete reviews before solve logs (this bit
us once — see the `reset_list_progress` fix in git history). Likewise
delete `list_problems`/`user_problems`/`solve_logs`/`reviews` before
deleting a `problems` or `users` row they reference.

## Migrations (Alembic)

```bash
cd backend
venv/bin/alembic upgrade head          # apply pending migrations (also: make migrate)
venv/bin/alembic current               # what revision is the DB on
venv/bin/alembic history               # list all migrations
venv/bin/alembic revision --autogenerate -m "add some_column"   # after changing a model
```

Migrations live in `backend/alembic/versions/`. Always review an
autogenerated migration before applying it — `alembic revision
--autogenerate` diffs the ORM models against the live DB and can miss
or misfire on things like check constraints.

## Seeding sample data

```bash
cd backend && venv/bin/python -m scripts.seed     # or: make seed (from kingfisher/)
```

Loads 80 curated problems into a global "NeetCode 150" list. Safe to
re-run — it upserts by slug and skips problems already in the list,
so it won't create duplicates.

## Common tasks

**Make a user admin** (there's no self-serve UI for this yet):
```sql
UPDATE users SET is_admin = true WHERE email = 'you@example.com';
```

**See what's in the database:**
```sql
SELECT count(*) FROM problems;
SELECT name, is_global, owner_id FROM lists;
SELECT email, username, is_admin FROM users;
```

**Resetting the database entirely** (drops all data, including the
Docker volume — irreversible):
```bash
cd backend
docker compose down -v      # -v removes the pgdata volume
docker compose up -d db
venv/bin/alembic upgrade head
venv/bin/python -m scripts.seed   # if you want the sample data back
```

If you just want to clear *your own* test data without nuking the
whole DB, `TRUNCATE` the tables in FK-safe order instead:
```sql
TRUNCATE reviews, solve_logs, user_problems, list_problems, lists, problems RESTART IDENTITY CASCADE;
-- leaves `users` alone; add it to the list above if you want a truly clean slate
```
